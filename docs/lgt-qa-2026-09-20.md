## Name editor

The game enters its editor with a Korean default name, then calls
`imSetCurrentMode(3)` from `0x3c227`. That selects `N123` in the returned mode
table. The Host previously treated the keypad automaton as a field constraint,
selected a numeric keyboard, and rejected Korean before calling the guest.
The [WIPI input-method API](https://mirusu400.github.io/wipi-wiki/c-api/graphics.md)
defines this mode as an index into the automaton's languages, not a widget
validation rule. Host-composed text now bypasses that keypad restriction;
ordinary numeric keypad events retain their existing behavior.

Removing that restriction alone does not fix this archive. Its caller at
`0x3c4ce..0x3c4f6` initializes two local five-byte strings, passes them at
`sp+0x124` and `sp+0x11c`, and reads returned lengths at `sp+0x18` and `sp+0x14`.
It does not initialize those lengths as capacities. This differs from the
published input-capacity annotation and from the existing capacity-taking
fixture. Interpreting the uninitialized size as capacity rejects even one
Korean character in the observed run.

The compatibility path recognizes that caller's complete argument setup and
checks the live stack pointers. It supplies only the five bytes evidenced by
the caller's initialization, independent of residual size values. It delivers
at most four EUC-KR bytes per callback, keeping characters intact. Further
characters use successive callbacks through the same widget. Unrecognized
callers still use their declared capacities, including zero. No archive name,
module hash, fixed guest address, or blanket zero-size fallback selects this
behavior. The widget retains its field-length and validation policy.

Authored tests cover composition in every keypad mode, strict encoding,
unchanged numeric key behavior, stale snapshots and atomic rejection for
ordinary capacity-taking widgets. The output-only caller fixture also checks
instruction mutations, mismatched stack arguments, ARM return addresses,
large residual length words, character boundaries and a byte guard after each
five-byte buffer.

## Initial graphics investigation (superseded by the wide-context fix)

Case 2's missing text is already visible in its initial connection-error dialog.
The source glyph surface contains ink: 163 pixels of RGB565 `0xfe4e` in the
first diagnostic copy. Its destination context at `0x1500360` contains
`0x6ea1` at byte offset 28. The runtime reads that as an x translation of
28,321 pixels and consequently draws outside the display.

Disassembly establishes that `0x6ea1` is a color-key pixel callback: it compares
the incoming second argument against a key read from guest globals and returns
either the first or second argument. Multiple engine helpers directly store
callback addresses at context offset 28. They do not install these through
`MC_grpSetContext`. The current runtime expects an offset there and requires
callbacks at offset 32 to have been registered through that API.

An ignored diagnostic overlay treats the observed word as a callback and
removes the bogus translation. Case 2's initial dialog then displays its text
and button label. Baseline and diagnostic captures are
`build/qa-lgt-2-baseline.png` and `build/qa-lgt-2-direct.png`; context values and
disassembly are in `build/qa-lgt-2-context.log`, `qa-lgt-2-disasm.txt` and
`qa-lgt-2-helpers.txt`. This confirms the mechanism, not a production fix.

That heuristic overlay was not merged into runtime code: checking merely
whether a word looks like a code pointer is not an unambiguous layout rule.
The specification treats `MC_GrpContext` as opaque. The final revision-selected layout below establishes the caller's layout while
preserving compact contexts and actual coordinate offsets.
Also, this callback reads mutable guest globals, so the existing cache keyed
only by function, parameter and pixel pair cannot be assumed valid for it.
The title and black lower-right region were subsequently replayed below.

## Mirrored sprite transparency

Case 3 reaches a battle using an isolated copy of its existing save. Left-facing
sprites retain their shape, while sprites reflected by the guest show magenta
silhouettes and missing ink. Disabling the pixel-operation cache does not change
this result. The guest obtains an image framebuffer pointer, swaps two-byte
RGB565 pixels horizontally through `memcpy`, draws the image, then reverses the
swap. The runtime refreshes those pixels but retains the original positional
alpha mask, so transparency no longer matches the reflected pixels.

Decoded images now retain a color key when every transparent pixel has the same
RGB565 value and no opaque pixel has that value. Drawing tests the current guest
pixels against that key. Multiple transparent colors or a collision with opaque
art retain the positional mask, including collisions introduced by RGB565
quantization. Opaque magenta remains visible when the encoding declares it so.

The [graphics specification](https://mirusu400.github.io/wipi-wiki/c-api/graphics.md)
describes an internal mask but does not define how it follows raw framebuffer
edits. This compatibility behavior follows the observed caller; it is not a
claim that all encoded alpha can be reconstructed from RGB565 memory.

The authored reflection test fails before the change and passes afterward,
including restoration of the original pixels. Additional tests preserve
ambiguous masks. The same real battle route removes the magenta silhouettes:
compare `build/qa-lgt-3-cache-battle.png` with
`build/qa-lgt-3-keyed-battle.png`. Replay commands and execution output are
`build/qa-lgt-3-battle.commands` and `build/qa-lgt-3-keyed-replay.log`.

## Java file modes explain the lost speed and sound settings

Case 5 opens its five-byte settings file using Java mode 4. Before the fix,
`File.read` returns -1 even though the isolated save contains
`01 01 02 01 01`. The Java adapter passes the value directly to `MC_fsOpen`,
where 4 means truncate. The Java enum instead uses 3 for truncate and 4 for
read-write. The published File API defines the four operations without numeric
values; the observed reader and the reference implementation agree on this
enum. No reference source code was copied.

The settings byte at index 2 reaches the guest helper at `0x8fb68`, which maps
0/1/2 to 200/150/100 ms and stores the result in the class data at offset 0x38.
The loop reads that value before `Thread.sleep` at `0x93ac4`. An empty settings
read therefore selects the slowest loop and disables music. The Host's extra
paint after each key independently explains why input appears to speed it up.
This is a file-boundary defect, not evidence for changing sleep durations.

The adapter now translates all four Java modes to the C flags. Authored tests
fail before the fix for both truncation and read-write, then pass after it.
Existing file-stream tests now use the Java mode number rather than a C flag.
C flag behavior and the save format remain unchanged.

A new production debug replay uses another isolated save copy at
`var/savedata/qa-lgt-20260920/file-fix-5`. The existing file now returns all five
bytes, the loop requests 100 ms, and the title constructs a Clip and successfully
starts Player playback. The Host emits `build/qa-lgt-5-probe-audio.mid`.
The prior runtime log is retained as `build/qa-lgt-5-file-baseline.log`; the new

## Wide graphics context

Case 2's engine writes pixel callbacks at byte 28. A diagnostic using the
56-byte layout corroborated by the reference implementation restores its
agreement text, title lettering and menu. The layout contains four signed
32-bit inclusive clip endpoints at 0, foreground/background at 16/20, alpha at
24, callback/parameter at 28/32, font/style at 36/40, XOR at 44, and signed
x/y translation at 48/52. The C API still exchanges exclusive clip endpoints;
SetContext/GetContext translate them at the boundary.

The runtime selects this ABI through the existing code-revision registry for
the verified native-module digests of cases 1 and 2. It does not guess from a coordinate
that resembles a function pointer. Unregistered modules retain the existing
compact ABI. This does not claim that arbitrary mixed layouts inside one
module are supported. No source code was copied from the reference.

Direct callbacks are accepted only as Thumb addresses inside the loaded
module. Their pixel cache is discarded between draws because the observed
callbacks read mutable guest globals. Authored tests cover the 56-byte write
boundary, signed translations distinct from callbacks, mutable callback data,
exclusive clip round trips, empty clips, and retention of compact behavior.
Production debug replay also restores the title and its menu; the title capture
is `build/qa-lgt-2-wide-title.png`. The diagnostic title capture is
`build/qa-lgt-2-full-title.png`. `make test`, `make test-debug`,
`go test -race ./internal/...` and `go vet ./...` all pass; logs are
`build/qa-lgt-wide-{test,debug,race,vet}.log`. Case 1 also reproduces the defect and is now registered. Its production replay

## Key input must not create unsolicited paints

The Java key adapter previously marked the card dirty after every delivered
press and release, even when the application requested no repaint. Case 5
updates gameplay inside paint, so repeated input also advanced simulation.
The adapter now delivers keyNotify and preserves the existing dirty flag,
leaving repaint scheduling to the application. The authored regression fails
before this change and passes after it: press/release callbacks receive their
arguments, unrequested paints remain absent, and pending repaint requests
survive key delivery.

## Vector replacement crash

A subsequent physical-device test ended at 2026-09-20 04:12:16 UTC while a Java
paint callback ran after right input. The failure was the unimplemented
`java/util/Vector` vtable slot 26, SVC slot `0x5ba301a`, called from `0xbb3c0`.
The receiver was a Vector, followed by an object reference and index 1.
The preceding report measured about 10 fps and normal guest speed. This was a
guest API dispatch failure, not an audio recovery failure or a server panic.

The established Vector declaration order places `setElementAt(Object, int)` at
26, between the verified `firstElement` (24) and `removeElementAt` (27) anchors.
The WIPI specification's CLDC Vector entry defines replacement at an existing
index and `ArrayIndexOutOfBoundsException` for an invalid index. The new handler
replaces the reference in place, accepts null and raises that guest exception
for negative or out-of-range indexes. It does not grow the list.

The regression test fails on the missing registration before the change. After
the change it invokes slot 26 through the native Java dispatch boundary with
arguments in ARM registers, checks replacement at first/middle/last indexes,
and verifies unchanged size/neighbours and rejected empty/invalid accesses.
This is the LGT AOT Java boundary; no JVM bytecode implementation changed.

Validation passes: `make test`, `make test-debug`,
`go test -race ./internal/...`, `go vet ./...`, and the final focused Vector/Stack
checks. The debug server was rebuilt. A copied-save real-archive replay reached
the field, held right for 100 ticks (5 guest seconds, 50 frames), and continued
for another 100 ticks without failure (`build/qa-vector-replay.log`). That route
did not reach slot 26 in its trace, so it is a movement smoke check, not a
reproduction of the exact reported scene. The slot regression is the direct
proof for the reported missing-method failure; confirmation at the original
in-game position remains a physical play check. Original saves were untouched.
