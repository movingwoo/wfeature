## Typed file streams and card removal

Case 6 first fails at File vtable slot 11, called from `0xb16c`, naming
`openDataInputStream()Ljava/io/DataInputStream;`. The
[WIPI File contract](https://mirusu400.github.io/wipi-wiki/java-api/org/kwis/msp/io/File.md)
requires a DataInputStream and IOException when the file is not open or an
input stream is already open. The adapter now shares the existing file-stream
binding but allocates the typed DataInputStream object. Existing big-endian
primitive readers serve its vtable. Stream close releases the binding so a
second close does not advance the file cursor twice and a later stream can
open at the consumed position.

The regression first failed on the missing registration. It now checks the
returned class, native typed read, current file position, duplicate-open
refusal, idempotent close, reopen, and refusal after File.close.

The same real route then reaches the title and fails when new-game input calls
Display slot 12 from `0x1514`, naming `removeCard(Card)Z`. The
[Display contract](https://mirusu400.github.io/wipi-wiki/java-api/org/kwis/msp/lcdui/Display.md)
returns whether removal succeeded. The current single-card display can now
remove its active card and cancel its pending paint; a null or unrelated card
returns false without changing either. This does not implement a general
multi-card stack or notification lifecycle. The authored regression first
failed on the missing registration and now checks those states.

`case-6-stream-fix.{log,png}` records the restored title and second failure.
`case-6-card-fix.{log,png}` records 1,000 ticks, 737 flushes and no runtime error,
with the next in-game instruction screen. This is not full gameplay proof.

## Decoded-image cache pressure

The longer case 6 route fails at tick 1,946 with `LGT surface space exhausted`
inside Image.createImage, from `0x15d04`. The allocation-failure collection
frees seven objects and zero surfaces. The decode cache keeps its surfaces
after the final Image object is collected, and previously had no eviction
path. Consequently a sequence of distinct images can exhaust the bounded
16 MiB surface region even after the owning objects disappear.

Surface allocation pressure now evicts cache-only surfaces after collection. Live
Image and Graphics owners, including objects awaiting a grace cycle, retain
their surfaces. Every cache alias is removed before the handle is reused.
Ordinary collection still retains cached images, preserving repeat-decode
sharing. The memory bound is unchanged.

Data-arena pressure does not evict cached surfaces: a cache hit can hold a
surface handle in a Go local while allocating its new Image object. A separate
regression guards this construction window.

A regression with a deliberately small surface region fails before eviction
and passes afterward. It checks cache aliases, live Image and Graphics owners,
and the retained allocation limit. Another regression decodes an image again
after eviction and checks every pixel. The real route is recorded separately;
a successful earlier title screen alone does not prove this later failure fixed.

The final production debug replay, `case-6-final.{log,png}`, completes 5,000
ticks with 3,889 flushes and no runtime error. It evicts 253 cache-only surfaces
at the former allocation failure. Saves are a separate copy of the prior
isolated reproduction. The final screen is an in-game continuation prompt;
this proves the recorded startup, card transition, and allocation failures
no longer stop that route, not complete gameplay or progress persistence.

## Long-array store word order

Case 3 still renders only two frames after 5,000 ticks (50,040 guest ms).
Its worker keeps sleeping for 10 ms and checking a timer; the timer is not
expiring. At `0x7b40..0x7b4e`, the guest sign-extends its 32-bit interval into
r2 and passes the low word in r3 to Java interface slot `0xfd`. The observed
1,000 ms interval arrives as `(array, 0, 0, 1000)`. At `0x7b70..0x7b7e`, it
similarly moves the currentTimeMillis high result from r1 into r2 and low r0
into r3. Slot `0x5b` returns the stored value low-first in r0/r1.

The adapter incorrectly treated the store arguments as low-first, turning
1,000 into `0x3e800000000` and reversing the epoch timestamp too. The fix swaps
only the two arguments at the interface boundary; array storage, long return
registers, and the normal internal array helpers stay low-first. This is an
observed compiler-helper ABI, not a WIPI public API signature.

The new boundary regression first fails with `element 0 = 0x3e800000000,
want 0x3e8`. It now covers a positive interval, epoch timestamp, asymmetric
64-bit value, and negative value through the store and load SVC handlers.
The existing internal storage and bounds regression also passes.

The production replay `case-3-wide-array-fix.{log,png}` completes 3,000 ticks,

### Transparency calibration origin

The first field's direct framebuffer blitter uses a key sampled during native
initialization. It draws magenta with `PutPixel(dst, 0, 0, context)` at `0x1742`,
then copies a pixel through its own framebuffer helper into `0x1500004`. That
helper (`0x167c`) adds 24 rows for the screen. The sample therefore reads a
different location from the pixel it just drew: the observed key is `0x0000`,
while framebuffer row zero contains `0xf81f` and row 24 contains zero. Later
native transparent copies compare against that sampled key. This loses black
pixels and copies magenta into the map.

The WIPI graphics specification defines drawing coordinates relative to the
context's offset and initializes that offset to `(0, 0)`; it does not supply a
24-row default translation. Changing general framebuffer pointers or context
origins would affect other rendering. Exact module SHA-256
`a94d19252edfcee2346cd166c4d4e1f1303dbfce987b50992d51de519b3ac942` instead selects
`lgt.color_key_sample_origin`: the calibration call alone changes its y argument
from zero to 24, with an instruction guard. Its read and write then agree;
archive bytes and saves remain unchanged.

A diagnostic replay confirms the sampled key becomes `0xf81f`. The same
1,334-tick gameplay route has zero magenta pixels instead of 5,690; grass,
river edges and object backgrounds render without pink patches. The authored
regression executes the original/corrected Thumb argument setup and the real
PutPixel handler, then reads the native sample location. Additional checks
cover unknown instructions and opt-in archive identity, descriptor independence
and unchanged archive bytes. Full campaign progression is still outside this
bounded rendering verification.

### Certificate path: subscriber-bound save encoding

Case 4's archived `savedata` is not identical to a fresh runtime save: both
are 2,720 bytes, but 2,709 bytes differ when compared directly before launching
the archived copy. The earlier post-run comparison had observed a rewritten
file and could not establish the original contents.

Native save I/O now identifies the reason this matters. Routine `0x832cc`
copies ordinary state at `0x150a37c` to the work buffer at `0x150b350`, encodes
it, and writes 680 words. Routine `0x8337c` reads that buffer, decodes and checks
it, and copies to live state only when validation succeeds. The codec at
`0x83420` obtains PHONENUMBER, builds a CRC table using polynomial `0xedb88320`
with signed right shifts, and XORs each payload byte with a sum of a lookup
byte and a repeating subscriber-number byte. A seed byte sits at payload
index 2715, followed by four CRC bytes. Encoding and decoding advance the seed
for each byte; the phone string participates in both paths.

Thus supplemental availability alone cannot establish that a supplied save is
valid for this runtime's subscriber number. This is evidence for a
subscriber-bound save contract, not permission to rewrite original saves or
skip certificate validation. Original archives and user saves remain intact.


A 2,000-tick production replay confirms the consent path calls NetConnect
with callback `0x2d5c1`; the runtime's offline failure returns the guest to the
missing-certificate dialog. The bounded diagnostic overlay then permits only
that exact module/callback to use the in-process socket machinery. It does
not open an OS socket and never sends a successful authentication reply.

The resulting first request is 73 bytes. It begins with big-endian length
`0x0049`, followed by bytes `00 00 00 03 f9 00 00 02 05`, version text
`V.1.0.1`, padding, the emulator subscriber number, and zero-filled trailing
fields. The native connection callback is `0x2d471`; the read callback at
`0x2d171` first asks for two bytes, then derives the remaining frame length
from that header. The write is observed at `0x2d8c5` and deliberately rejected

## Certificate message compatibility

Production now selects `lgt.certificate_message` only for the evidenced full
native-module SHA-256 and matching application descriptor. The session's
subscriber number and handset model construct two exact bounded requests;
version, application header, command, field widths and padding must also match.
The existing socket contract additionally checks the dial/connect callbacks
and endpoint. It opens no OS socket. Unknown revisions, reordered commands,
changed fields, trailing bytes and uploads do not receive success responses.
The ordinary authentication opt-out leaves this responder disabled; the
selected session status is `lgt-certificate-message`.

Each socket owns its request stage, fragments and pending response. Replies
become readable only at the next socket-service boundary. This prevents a
native response callback from running inside the send routine before its UI
state transition finishes. Closing a socket drops its pending reply and
callbacks. No original archive or save is rewritten by the compatibility
layer; the guest owns its normal packed-save writes.

The first reply acknowledges the handshake. The second carries a bounded
nonempty informational message explicitly stating local handling. The guest's
observed parser sets its certificate-present field and follows its existing
save path. No carrier credential or remote account is represented by this
reply. Authored regressions cover every request split, changed request bytes,
sequence/size rejection, deferred read readiness, two-part frame reads, and
cancellation before delivery. Existing local protocol tests pass unchanged.


Production acceptance passes: the release CLI without overlays reaches the
menu and item screen by tick 2,288 (`case-4-production.log`,
`case-4-production-6.png`, `case-4-production-8.png`). The guest writes its
ordinary save. A new process using a copy of that save and `-no-auth` reaches
the menu by tick 776 without the missing-certificate prompt
(`case-4-restart.log`, `case-4-restart-2.png`). Because the responder is disabled
in that second run, this establishes guest-save persistence of the certificate
state, not merely a repeated compatibility handshake. Full gameplay and later
