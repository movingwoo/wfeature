## Startup regression

The three reported archives are `c7d06bd34291`, `61ba00511b84`, and
`3185174d2121`. Each installs a visible card and starts a worker. The worker
exhausts instruction slices without requesting a repaint or sleeping. The
Host's `forcedSlice` guard prevents automatic painting; no display-originated
initial repaint was queued when the card became visible.

A 1,200-tick CLI run of the first archive produces zero flushes and no screen.
A bounded 20-tick probe reproduces the same state in all three: one card, one
worker, `forcedSlice=true`, `repaintPending=false`, and no flushes. Allowing one
paint releases all three: another 20 ticks produce 11, 5, and 4 flushes.
This isolates an initial-paint dependency, rather than proving that every
busy worker should receive unsolicited paints.

The display now queues a repaint after successfully notifying a newly shown
or uncovered card. Worker instruction limits and subsequent frame ownership
remain in place. The [WIPI Card specification](https://mirusu400.github.io/wipi-wiki/java-api/org/kwis/msp/lcdui/Card.md)
describes visibility notification and repaint servicing; this implementation
supplies the display invalidation required to make the newly visible card
appear. The specification does not prescribe this emulator's worker scheduler.

`TestShownCardPaintUnblocksBusyWorker` reproduces a worker waiting for state
initialized by paint. It fails before the fix (`initial paint=false`) and
passes after it. Existing forced-slice and asynchronous cadence tests pass.
The KTF package test suite passes. With the production fix, all three local
20-tick probes produce frames without forced diagnostic intervention.
Extended startup acceptance and repository-wide gates are recorded below.

Evidence: `build/ktf-next-cases.json`, `build/ktf-next-7-startup.{log,json}`,

## Native environment return and the slow case

Archive `4120f27288ab` initially renders only three frames over 19.350387 guest
seconds (1,200 ticks). Instrumenting the Java sleep boundary records repeated
11,036 ms waits. This is not an observed CPU saturation problem.

The compiled native at `0x1058bd` ends by storing a 32-bit result at environment
offset 40, then tag 2 at offset 36. It leaves the scratch offset `0x2b1c` in r0.
The frame loop reads the native result, subtracts elapsed time, and passes it
to `Thread.sleep`. The runtime's register-only return path therefore reports
11,036 instead of the environment's value (initially zero, subsequently 75).
The native's instructions at `0x105ac6` through `0x105ad0` and runtime snapshots
establish this convention for the affected caller. It was the missing caller
evidence noted in the earlier native-ABI review.

Production `CallNative` now recognizes an explicitly published tag-2 word.
The tag is cleared on entry, so an earlier result cannot override a later
register return. A nested scope restores its caller's tag and value on exit,
and both words use the existing logical-thread storage boundary. Older modules,
unprepared synthetic runtimes, absent tags, and unsupported tags retain their
register return. This does not establish other environment result tags or a
wide environment return convention.

Authored Thumb fixtures cover nonzero, zero and negative word results,
unsupported tags and a subsequent register-only return. Scope tests cover
nested results and separate logical threads. Existing native-call tests pass.
A production run reaches the animated opening and produces 215 flushes over
15.950319 guest seconds at 1,200 ticks. It later reaches a mostly empty menu
background, so playable combat and the rest of the slow report remain open.
A diagnostic run observes 10, 66 and 75 ms frame waits after the correction;
the unrelated worker's 500 ms wait remains unchanged.

Evidence: `build/ktf-next-image5.bin`, `build/ktf-next-symbols5.txt`,
`build/ktf-next-native-slot5.log`, `build/ktf-next-native-production5.log`,

## Reproduced image-lifetime crash

The page log provides 72 input edges for its final C session. Replaying those
edges with a copy of the debug save reproduces the same failure at `0x12209b`
after 14.767274801 guest seconds and 56 delivered edges. Allocation addresses
differ from the server report, but the record shape and failing call match.

The trace creates a framebuffer at `0x30062fdc` and its image wrapper at
`0x30062ffc`. On the next timer callback, `MC_grpDestroyImage` receives
`0x30062fdc`, which previously also held an image record but now holds the new
framebuffer. The destructor accepts that framebuffer and releases it and its
pixels. The still-live wrapper then points at the released framebuffer.
The surface classifier tests whether that first word is currently allocated;
it therefore misclassifies the wrapper as a plain framebuffer and fails on
its zero depth. This initially narrowed the failure to stale-handle destruction and wrapper
classification. The source ownership correction below identifies and removes
the earlier cause rather than suppressing the final depth error.

Evidence: `build/ktf-next-replay-events.json`, `build/ktf-next-replay6.log`,
`build/ktf-next-lifetime6.log`, and `build/ktf-next-replay6.json`. The lifetime
instrumentation retains allocation sizes, destruction arguments, and caller
addresses. Screens are `build/ktf-next-replay6-*.png`.

## Source ownership correction

Image records retain their encoded source address for destruction. This title
also frees that source itself after creation. The address then becomes another
allocation, including another image, but the old destructor still frees it.
The earlier unexpected destruction of a live framebuffer follows these stale
ownership links; it is not evidence that malformed depth should be accepted.

`imageSourceBuffers` now records the source allocation each live image still
owns. Any release revokes every reference to that allocation before the arena
can reuse its address. Destruction consults ownership rather than trusting a
stale address in guest word thirteen. Freeing an image also removes its entry.
Non-WIPI sources are not adopted. Guest image records and drawing rules retain
their existing layout and behavior.

The [WIPI image creation contract](https://mirusu400.github.io/wipi-wiki/c-api/graphics.md)
says a static image's source is released after its first frame is decoded.
An experiment that moved release directly into creation caused this archive's
startup to fail in a later `memcpy` of its source. That experiment is excluded.
The emulator preserves its delayed-release compatibility, while a caller that
releases the source first now revokes that delayed ownership. This divergence
is established by the caller, not inferred as a change to the standard.

`TestImageDestroyPreservesReusedSourceAllocation` creates an authored PNG,
releases its source, reuses exactly that address, and destroys the old image.
Before the fix, destruction frees the replacement; after the fix it remains
live. Existing complete-destruction, repeated-allocation, and out-of-bounds
source-field tests pass.

The unchanged 72-edge crash replay now completes 40.0008 guest seconds,
4,099 ticks and 1,700 flushes without error. The old run fails after 56 edges
and 14.767274801 seconds. A separate interactive CLI route reaches character
selection, a locked-character dialog, the stage map and a playable character
in the first arena. All writes remain in isolated saves.

Evidence: `build/ktf-source-lifetime-replay.log` (rejected eager release),
`build/ktf-source-owner-replay.log` (ownership experiment),
`build/ktf-source-production-replay.log` (production), and
`build/ktf-console6-{popup,play}.{png,json}`. The source correction passes
`make test`, `make test-debug`, internal race and vet; logs are
`build/ktf-source-{test,debug,race,vet}.log`.

### Repeating Java timer ownership

A repeating Java timer creates a worker for each invocation. The previous
cadence fix attached ownership to that worker, so its return restored automatic
painting even though the next invocation of the same task was still scheduled.
Three archives show substantially more paints than requests in this gap.

A successfully returned task now passes its card ownership to the pending
entry with the same Timer and task identities. Cancelling or replacing that
task releases ownership. This also preserves synchronous repaint ownership.
The authored scheduler regression fails before the fix with twenty world steps
from one request. After the fix, three invocations each advance the world once;
replacing the task on the same Timer restores fallback painting.

## Deadline recheck and serial repaint ownership

The 37 inconclusive corpus entries were retried with a 30-second wall deadline,
a fresh save, and a clock advanced by 1 ms per tick for a target of 20 guest

in `build/ktf-cadence-deadline-summary.json`; results are in
`build/ktf-cadence-deadline-recheck/`. This recheck predates the serial fix below.

Archive `d373b4d1370e` exposes another unsolicited-paint path: its self-queued
serial Runnable polls each idle pass and requests repaint only when its own
frame interval expires. Over 20 seconds it makes 209 requests but receives
1,250 paints. The earlier worker and timer ownership rules do not cover a
serial invocation, which runs on the client thread and returns between polls.

A serial invocation now retains the shown card whose repaint it requested or
serviced, but only while that same Runnable is queued again. Polls without a
new repaint preserve this ownership. Returning without requeueing releases it;
a different instance of the same class does not inherit it. An explicit repaint
still runs. The existing serial dispatch timing and timeout behavior are unchanged.
Ownership storage is limited to queued Runnables and removed when each is taken.

The authored regression exercises the actual serial scheduler, polling passes,
asynchronous and synchronous repaint, and replacement by another instance.
Before the fix one request produces twenty asynchronous paints or thirteen
synchronous paints. After the fix each requested frame advances the world once,
and stopping the original loop restores fallback painting.

The same fresh-save, 1 ms clock route for `d373b4d1370e` now gives 214 paints
from the same 209 requests. The remaining five paints occur during bootstrap.
All 27 corpus entries observed using `callSerially` complete the 20-second
recheck without error. This does not establish completed gameplay for every
entry. Results and runner identity are in `build/ktf-cadence-serial-fixed/`

not drawn by the WIPI string APIs. Changing font ascent or baseline cannot

The guest draws a 172×168 dialog panel centered at screen height / 2. Its
separate text routine uses fixed title Y=85 and body Y=115, plus an origin
that the guest explicitly initializes to zero. Memory watches identify those
initial stores; no later writer changes the origin. At 240×320, the panel
starts at Y=76, leaving its title over the upper border and its first body

contract and adapts this guest routine, following the existing revision-scoped
compatibility boundary. Compiled-image SHA-256
`d4fd51c94269e3143b57802c00898f2ce43dee2e5726076d133b44a0304809c6`
and both relocated layout digests must match. Seven `STR r3,[sp,#4]`
instructions across the common dialog and settings layouts are replaced in
emulator memory. Their stored text Y gains
`floor(screenHeight/2) - 140`; registers, flags, horizontal coordinates,
panel rendering and the on-disk archive retain their original behavior.
Unknown or changed images receive no correction. This is a compatibility
adaptation, not a claim about original handset behavior.

At 240×320 the title now starts at Y=105 and the body at Y=135, inside their
respective boxes. The same routine's character-selection notice also aligns.

pixel-identical character-description and resumed-combat frames; differences
are confined to dialog text in the two dialog captures. Authored regression
tests cover even and odd screen heights,
an unchanged 280-pixel layout, neighboring memory, register/flag preservation,
